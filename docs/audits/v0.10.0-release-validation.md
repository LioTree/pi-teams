## CR-01..04 verification

### CR-01 — confirmed deletion after a failed lease compare (blocking)

**Fix reviewed.** `shutdownTeam` now computes `closeStillOpen(closed)` and throws before setting `dissolvingTeam`, before detaching the lead, and before removing either directory. `performClose` also reports `lease changed` or `close failed` and keeps the lead attached.

**Regression:** `extensions/team-close.test.ts` — `confirmed shutdown does not delete the team when a pane lease changes`.
It mocks `replaceRuntimeInstance` to return `null`, runs `/team-shutdown confirm`, and asserts the config/team directory still exist, the peer is not marked stopped, the kill was not called, and `ctx.shutdown` was not called.

**Mutation check:** removing the `unfinished` guard in `shutdownTeam` made this test fail (1 failed, 31 skipped). Raw evidence: `M01.log` and `M01-index.patch`.

### CR-02 — failed terminal close reported as closed (blocking)

**Fix reviewed.** `TerminalCloseResult` (`closed | absent | failed`) is now part of the adapter contract. `TmuxAdapter.kill` checks `execCommand`'s status, maps “can't find pane/window/session” results to `absent`, and reports other nonzero results as `failed`. `killTeammate` restores the prior runtime lease and returns `close-failed` instead of `closed`; close lines, lead exit, and deletion are gated on the result.

**Regressions:**
- `src/adapters/tmux-adapter.test.ts` — `reports a refused kill-pane instead of ignoring the status`.
- `src/adapters/tmux-adapter.test.ts` — `treats a missing pane as already closed`.
- `extensions/team-close.test.ts` — `a refused tmux pane close does not exit the lead, delete the team, or leave the member stopped`.

The extension test uses the real `TmuxAdapter.kill` with only `execCommand` mocked to `status: 1`, asserts `peer: close failed`, no lead exit, no deletion, and that the runtime activity/instance are restored; then repeats the assertion for `/team-shutdown confirm`.

**Mutation check:** changing the final `kill` result from `failed` to `closed` made this extension test fail (1 failed, 31 skipped). Raw evidence: `M02.log` and `M02-tmux.patch`.

### CR-03 — later append failure duplicates an earlier stop notice (should fix)

**Fix reviewed.** Stop notices now use a stable `stop:<instanceId>` message ID, a durable per-team `stop-notices.json` state with `expected`/`notified` lists, `appendMessageOnce` deduplication by ID, and a failure rollback limited to the instances that were not delivered. A later failure does not make an already stored notice eligible for a second append.

**Regression:** `extensions/team-close.test.ts` — `a failed later stop notice does not resend an earlier one`.
It stops two instances, fails the second append once, waits for both notices, then verifies each appears exactly once and the stored IDs are singular.

**Mutation checks:** rolling back the whole claimed batch while keeping the stable ID still passed, because the ID deduplication independently prevents the duplicate. The refined mutation (rollback-all plus a per-call unstable ID) made the test fail (1 failed, 31 skipped). This confirms the test exercises the observable duplicate-notice defect, while the implementation retains redundant protection. Raw evidence: `M03.log`, `M03b.log`, and the matching `*-index.patch` files.

### CR-04 — in-flight stop reporter recreates deleted team data (should fix)

**Fix reviewed.** `dissolvingTeam` fences new reporter work; `teamAcceptsWrites` is checked at claim time and again at the durable write boundary; `appendMessageOnce` accepts a commit predicate and checks it both before creating the inbox directory and inside the lock, so a write that loses to deletion cannot recreate `teams/<team>/inboxes`; `shutdownTeam` drains the reporter chain before removing the directories.

**Regression:** `extensions/team-close.test.ts` — `an in-flight stop notice does not recreate a deleted team`.
It pauses a notice append before its disk write, starts `/team-shutdown confirm`, confirms deletion reached the status-clear step, releases the append, and asserts no append error, no stored notice, and the team/inbox directories remain absent.

**Mutation checks:** removing one commit check still passed because the second check enforced the boundary; removing both commit checks plus `dissolvingTeam` and `drainStopReports` made the test fail (1 failed, 31 skipped). Raw evidence: `M04.log`, `M04b.log`, and the matching `*-index.patch` / `*-messaging.patch` files.

## Additional review notes

- **Close command/tools.** `/team-close <member>` resolves a roster member and leaves the lead attached; `/team-close` closes every teammate and requests lead exit only when no line is `lease changed` or `close failed`. `team_close` and `team_resume` are registered; `team_shutdown` and `process_shutdown_approved` are absent (`extensions/index.test.ts`). No model tool deletes a team.
- **Deletion guard.** `/team-shutdown` requires the final word `confirm`; without it, parsing throws before any close or deletion. A failed close leaves the roster and retry state in place.
- **Resume.** Named `/team-resume <team> <member>` filters restoration to one member and suppresses the automatic all-member restore during a fresh attach; the test verifies one spawn and one roster entry. The original lead's automatic restore remains the recovery path after a close.
- **Model tool.** `team_set_model` submits a request and reports `pending`; a query without `model` reports `no_request`, `pending`, `applied`, or `refused`. Tests verify leader-only access, refusal, no teammate message, no automatic resume, and unchanged quiescence generation.
- **`team_wait`.** A team created mid-turn publishes `running`, so the following `team_wait` can enter `waiting`; a stale `idle` is accepted, and an ownership-preserving failure names the current activity. Covered by `extensions/session-recovery.test.ts`.
- **Documentation.** AGENTS.md, README, guide, reference, skills, and the current CHANGELOG section consistently describe `team_close`/`team_resume`, `/team-shutdown confirm`, and the absence of a delete-team tool. Historical audit files were left unchanged.

## Residual risks and limitations

1. **Non-blocking: `dissolvingTeam` is a session latch.** `extensions/index.ts` sets `dissolvingTeam` on successful shutdown and never resets it. If the same lead session later creates a new team with the same name, stop notices for that recreated team are suppressed for the lifetime of the session. This is a narrow notification gap with no data loss or roster effect; it was not fixed because implementation changes require lead approval. Follow-up: clear the latch when a new team with that name is created or attached.
2. **Close-failure verification is adapter-dependent.** Tmux now reports nonzero `kill-pane` status; other adapters still return `void` or throw, so their failures are only visible as exceptions. Windows Terminal and Zellij continue to refuse bulk close. This matches the existing platform limits.
3. **No end-to-end UI/process validation.** Tests use the fake terminal context, SDK streams, and a mocked `ctx.shutdown`. The happy-path invocation, refusal paths, state transitions, and recovery are verified, but an actual Pi shell return / real pane close / provider call was not performed under the task constraints.
4. **Mutation testing was isolated.** `/tmp/release-mutation-evidence` is a copy with a symlinked `node_modules`; it does not alter the repository source or hashes in this report. The persistent logs and patches are in the evidence bundle described above.
5. **Test timing.** Successful deletion tests take roughly 5 seconds each after the deletion, apparently from post-deletion session-shutdown cleanup; no assertion failed. This is a test-duration observation, not a release blocker.
